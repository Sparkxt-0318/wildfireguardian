### T1.5a - local solar times (`research/shared/geo/solar.py`)

**Route taken: the NOAA solar position algorithm, implemented directly.**
Checked both alternatives the brief names, in this sandbox's venv
(`/home/user/wildfireguardian/.auto/venv`), 2026-09-16:

```
python -c "import astral"   -> ModuleNotFoundError
python -c "import pvlib"    -> ModuleNotFoundError
```

Neither is installed, so the module implements the NOAA Solar Calculator's
general solar position equations (declination, equation of time, sunrise
hour angle) in pure Python stdlib `math`, no network and no third-party
geoastronomy dependency. This is documented in the module's own "ROUTE TAKEN
AND WHY" section, per the task's instruction to say which route was taken
and why.

Provides `local_solar_times(lat, lon, date) -> SolarTimes(sunrise, sunset,
polar)`, `local_sunrise`, `local_sunset`, and `is_daytime(lat, lon,
when_kst)`. Every function's docstring states the KST (UTC+9, no DST since
1988) convention and the WGS84 lat/lon unit convention.

**Validation against known pairs.** No live oracle was available inside this
module (astral/pvlib absent), so four known Korean sunrise/sunset pairs were
retrieved from the sunrise-sunset.org API (same 90.833-degree zenith
convention), converted from UTC to KST, and hardcoded into the test file with
their retrieval method documented inline:

| location | date | sunrise (KST) | sunset (KST) |
|---|---|---|---|
| Incheon (37.4563N, 126.7052E) | 2025-06-21 | 05:10:59 | 19:58:58 |
| Incheon | 2025-12-21 | 07:42:22 | 17:20:00 |
| Gangneung (37.7519N, 128.8761E) | 2025-06-21 | 05:01:23 | 19:51:11 |

### T1.5b - dirty timestamps (`research/shared/qc/timestamps.py`)

Two-layer design: `parse_kfs_ymdhm(df, prefix)` parses one
`<prefix>_년/_월/_일/_시간` quadruple into a `datetime64` series (documented
column contract, reusable for any KFS file using that naming, including the
still-unseen state-history file once its actual prefixes are confirmed);
`flag_dirty_timestamps(df, start_col, end_col, ...)` takes two already-parsed
timestamp columns and adds four boolean flag columns plus a duration column,
never dropping a row. `flag_kfs_ymdhm_timestamps` composes both for the
common case.

Flags: `qc_flag_missing_containment`, `qc_flag_impossible_end_year`,
`qc_flag_negative_duration`, `qc_flag_end_before_start`. The last two are
documented as the same boolean condition given only two parsed timestamps
(duration = end - start); both are still emitted as separate named columns
because the brief and the registry name them as separate defect categories.
This is recorded in the module docstring as a documented design decision,
not silently assumed.

### T1.5c - fire complexes (`research/shared/qc/complexes.py`)

Implements exactly the one rule `docs/benchmark/K_SPREAD_2025.md` section 2
states: "영덕 2025 and 의성·안동 2025 are one complex" (quoted verbatim in
the module docstring with its source). `assign_complex_id(df, year_col,
region_col)` returns one complex id per row via a small, extensible
`COMPLEX_MEMBERSHIP` rule table (year + region-substring match), so a later
round can add another named complex without writing a second function. Rows
that match no rule get a unique `standalone::<index>` id rather than `None`,
so a leave-one-complex-out split never needs a special case for "not in a
complex". Deliberately does NOT implement a general same-day/same-area
auto-clustering heuristic: the K-SPREAD document names one specific complex,
and that is what was asked for.

Tested on synthetic records including the two Uiseong rows at 52,707 ha and
46,575 ha (the task's own example), asserting they, plus synthetic 영덕 and
안동 2025 records, all get the identical complex id, while unrelated fires
(different year or different county) get distinct ids, and that three
repeated calls (simulating roads/landslides/suppression each calling the
function independently) produce byte-identical groupings.

### T1.5d - geocoding precision ladder (`research/shared/geo/geocode.py`)

`GeocodePrecision` is an ordered `IntEnum`: `PARCEL` (0) <
`EUPMYEONDONG_CENTROID` (1) < `SIGUNGU_CENTROID` (2) < `UNRESOLVED` (3), plus
a `PRECISION_LADDER` tuple. `GeocodeResult` always carries `precision`
alongside `lat`/`lon` (both `None` only at `UNRESOLVED`). `geocode_address`
walks the ladder top to bottom via a pluggable `VWorldClient` plus optional
읍면동/시군구 centroid lookup tables, stopping at the first that resolves.

`VWorldClient` reads `VWORLD_KEY` from `os.environ` only, never accepts it as
a plain constructor default, never logs or prints it, and its `__repr__` is
overridden to say `<redacted>` rather than expose it accidentally.
Constructing it with the key unset raises `VWorldKeyMissingError` naming the
environment variable and where to get a key, without echoing back whatever
was (not) found. Confirmed `VWORLD_KEY` is in fact unset in this sandbox
(`os.environ.get("VWORLD_KEY") in (None, "")`, asserted directly in the test
file). The real HTTP call (`geocode_parcel`) is written as an interface
(`NotImplementedError` in the base class) and is exercised only via a mock
subclass in tests, never live.

### T1.5e - reference systems (`research/shared/geo/crs.py`)

`ANALYSIS_CRS = "EPSG:5186"`, `EXCHANGE_CRS = "EPSG:4326"`.
`assert_projected_crs(crs)` raises `ValueError` for a geographic CRS or a
missing CRS; `safe_length_m` / `safe_area_m2` call it before computing
anything. `transform_point`, `to_analysis_crs`, `to_exchange_crs` wrap
`pyproj`/`geopandas` reprojection. Tested: the guard fires on EPSG:4326 and
on `None`, passes on EPSG:5186; a length/area computation on a known
100 m x 100 m square in EPSG:5186 returns exactly 10,000 m2 / 400 m; a round
trip of Seoul City Hall (126.9780E, 37.5665N) through EPSG:4326 ->
EPSG:5186 -> EPSG:4326 returns the original coordinate within 1e-6 degrees.
