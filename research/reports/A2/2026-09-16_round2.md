### The finding that had to be investigated first: the column contract A2 designed against in round 1 was wrong for this file

Round 1's `research/shared/qc/timestamps.py` assumed the state-history file
would reuse the statistics file's `<prefix>_년/_월/_일/_시간` quadruple, because
the file was not yet on disk and that was the only documented KFS shape
available. Now that it is on disk, that assumption is confirmed **wrong**:
`진화시작시간`/`진화완료시간` are already combined `"YYYY-MM-DD HH:MM"` strings,
one column each, not four columns per timestamp. `flag_kfs_ymdhm_timestamps`
(the round-1 quadruple transform) genuinely does not apply to this file; it was
never going to produce 41 or any other number against it, because the columns
`parse_kfs_ymdhm` looks for (`진화시작시간_년`, etc.) do not exist in this file
at all.

This is reported as a finding, not smoothed over: the module's documented
column contract needed a second, real layer-1 parser, not a reinterpretation
of the first one. Added to `research/shared/qc/timestamps.py`:

- `parse_kfs_datetime_column(df, col)` - parses one already-combined
  `"YYYY-MM-DD HH:MM"` (or date-only `"YYYY-MM-DD"`) string column. This is the
  confirmed real contract for `진화시작시간`/`진화완료시간` (and `산불신고일`,
  though that column is not part of the duration calculation).
- `flag_kfs_state_history_timestamps(df, start_col="진화시작시간",
  end_col="진화완료시간", ...)` - composes the new parser (twice) with the
  existing, unchanged `flag_dirty_timestamps` layer. **This is the transform
  this program's directions actually run against the state-history file.**
  `flag_kfs_ymdhm_timestamps` is kept, unchanged, for the statistics file,
  which still uses the quadruple shape.
- `_strip_column_names(df)` - a small defensive helper, called at the top of
  every public function that looks up a column by name
  (`parse_kfs_ymdhm`, `parse_kfs_datetime_column`,
  `flag_kfs_state_history_timestamps`). The real file's header row carries
  trailing whitespace on every column (`'산불신고일     '`, etc., exactly as
  the round-2 brief warned); stripping defensively means a caller may pass
  either a raw `pandas.read_csv` frame or an already-stripped one (e.g. from
  `research.shared.loaders.kfs.load_fire_state_history`, which also strips)
  and get the same result either way, rather than a `KeyError` depending on
  which load path was used.

The module docstring was rewritten to state this two-shape reality up front
instead of the round-1 assumption; `parse_kfs_ymdhm`'s own docstring was
corrected to say plainly that its `prefix` argument is NOT a generic hook for
"whatever the state-history file turns out to use" (that was round 1's
open question, and it resolved to "no").

## T1.5g - the 리 rung

Added `GeocodePrecision.RI_CENTROID` to `research/shared/geo/geocode.py`'s
ladder, in the ordinal position A4 identified: between `PARCEL` and
`EUPMYEONDONG_CENTROID` (finer than a 읍/면/동 centroid, coarser than a real
parcel, matching Korea's own address hierarchy 시/도 > 시/군/구 > 읍/면/동 >
리 > lot number).

```
PARCEL = 0
RI_CENTROID = 1              (new)
EUPMYEONDONG_CENTROID = 2    (was 1)
SIGUNGU_CENTROID = 3         (was 2)
UNRESOLVED = 4                (was 3)
```

**Why it exists, in the docstring:** A4 measured the KFS landslide occurrence
record (`kfs_landslide_history`, 5,118 rows,
`research/landslides/design/address_precision.py`) and found zero records
carry a lot number in any address field, so `PARCEL` is unreachable for the
entire record; 95.64% of records instead bottom out at a named 리 and 4.28%
at 읍/면/동. Before this rung, the 95.64% had no correct place on the ladder -
forcing them to `EUPMYEONDONG_CENTROID` would silently understate the address's
real precision, and there is no other landslide dataset to fall back to. The
module docstring now names this dataset and this reasoning directly, not just
"a caller asked for a rung."

**Backward compatibility, checked before editing, not assumed:**
grepped the whole repository (not just `research/`) for every importer of
`GeocodePrecision` / `PRECISION_LADDER` / `geocode_address`. Exactly two
callers exist outside this module's own files: `research/shared/tests/test_geocode.py`
(mine, updated) and `research/landslides/design/address_precision.py` (A4's,
read-only), which reads ladder members only by NAME
(`[p.name for p in GeocodePrecision]`), never by raw integer value. So
shifting `EUPMYEONDONG_CENTROID`/`SIGUNGU_CENTROID`/`UNRESOLVED`'s underlying
integers (1->2, 2->3, 3->4) breaks nothing: every existing name still resolves
and every existing `<`/`<=`/`==` comparison between names still holds, since
the ladder is still monotonically increasing in the same relative order.

`geocode_address` gained `ri` and `ri_centroids` keyword-only parameters,
inserted into the fallback chain between the parcel attempt and the 읍면동
attempt. Both default to `None`; a caller that never passes them (every
caller before this round) walks the exact same three fallback steps as before
in the exact same order, so existing behaviour is unchanged - verified by a
new test (`test_no_ri_inputs_behaves_exactly_as_before_the_rung_was_added`)
that reproduces the pre-existing eupmyeondong-fallback test with the new
parameters simply absent, and by all pre-existing geocode tests continuing to
pass unmodified except for the two hardcoded ladder-membership lists, which
were extended (not restructured) to include the new member.

New tests added to `research/shared/tests/test_geocode.py`:
`test_ri_centroid_sits_between_parcel_and_eupmyeondong` (ordinal position),
`test_falls_back_to_ri_centroid`,
`test_ri_centroid_takes_priority_over_eupmyeondong_when_both_resolve` (ladder
stops at the first rung that resolves), `test_ri_lookup_miss_falls_through_to_eupmyeondong_centroid`
(a miss is skip, not fatal), and
`test_no_ri_inputs_behaves_exactly_as_before_the_rung_was_added` (backward
compatibility, above). `test_precision_ladder_ordering` and
`test_precision_ladder_is_ordered_int_enum` were extended in place to include
the new member at its correct position.

The invariant from round 1 still holds and is still tested: every branch of
`geocode_address` returns a `GeocodePrecision` alongside the coordinate
(`test_precision_always_present_never_none`, unmodified), and no function
mixes precision levels silently.
