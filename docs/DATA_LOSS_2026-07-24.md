# Permanent record: the OSM walk graph behind the 459-origin run is unrecoverable

**Status: permanent. Do not delete this file. Do not soften it.**

Discovered 2026-08-01 during Round-3 PHASE 1-B, while building the snapshot
store that exists to prevent exactly this.

## What happened

`scripts/run_real_roads_real_hazard.py` caches its OpenStreetMap walk graph at
`data/cache/osm/walk.graphml`. `data/cache/**` is git-ignored
(`.gitignore:62`) — correct for a cache, wrong for evidence.

The committed result `data/processed/real_roads_real_hazard.json` was written
**2026-07-23 20:54:55** (committed `eceb490`, 2026-07-23 21:32). The OSM cache
now on disk was written **2026-07-24 21:37–21:45**, roughly **25 hours later**.
The Jul-23 graph was overwritten in place. It was never committed, and the raw
Overpass responses behind it were overwritten too.

**It is gone. There is no copy anywhere.**

## Evidence

| | committed 459-origin run | current cache (snapshot `osm-walk_…2bff8d85`) |
|---|---:|---:|
| walk nodes | 8439 | 8443 |
| walk edges, after the `MultiDiGraph → nx.Graph` collapse | 11015 | 11020 |
| refuge POIs | 50 | 50 |
| file time | 2026-07-23 20:54:55 | 2026-07-24 21:40:57 |

The edge figure was obtained by replicating `_osm_walk_network`'s collapse rule
exactly (22,276 directed edges → 11,020 undirected, parallel edges dropped).
The counts differ by +4 nodes and +5 edges: OSM itself changed between the two
fetches, or the query resolved slightly differently.

One alternative explanation could not be fully excluded at the time of writing:
`osmnx` was not installed in the environment, so `ox.load_graphml` +
`ox.project_graph` could not be run against the snapshot to confirm they
preserve node count exactly. The 25-hour timestamp gap is independent of that
question and is on its own decisive.

## Consequence — state this wherever the 459 numbers appear

**The committed 459-origin figures (438 / 18 / 3) cannot be exactly reproduced.**
Re-running the script today uses a different road network. Any re-run therefore
differs from the committed numbers for at least two reasons, and attributing the
difference to a single cause is a false claim.

This is why PHASE 2's comparison is reported in **three** columns, never two:

| | committed (Jul-23 network, flat) | Jul-24 network, flat | Jul-24 network, slope |
|---|---|---|---|

* committed → column 2 isolates **network drift**;
* column 2 → column 3 isolates the **slope correction**.

A two-column "before slope / after slope" table built from the committed
baseline would silently attribute network drift to the slope model. Do not
produce one.

## What changed so this cannot recur

* `data/snapshots/` — content-addressed, hashed, immutable, **committed**
  (`data/snapshots/README.md`).
* `scripts/snapshot_external.py --preset osm` preserves the graphs, the refuge
  and depot layers, and the raw Overpass responses.
* `MANIFEST.json` records the digest, acquisition time and acquisition
  parameters of every external input.
* `config/default.yaml` + `config_hash` pin the parameter set that accompanies
  any reported number.

None of this repairs Round 2. The Jul-23 graph stays lost. The point of
recording it here is that the next person reading the 459-origin numbers learns
their limitation from the documentation rather than from a failed reproduction.
