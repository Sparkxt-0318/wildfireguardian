## The result, and how it differs from what the row expected

The row and the research brief expected "any bound-satisfying lambda turns the
hazard field into a near-blanket mask". That is true of the corrected column only.
**The pair is the result:**

- **Without** the finite-sample term the budget is met on the five calibration
  fires and then **broken on 3 of 6 held-out fires**, worst case FNR **0.750**. So
  naive calibration does not deliver what it claims.
- **With** it — `1/(n+1)` = **0.167** at n = 5 calibration fires, which eats
  **83 % of a 0.20 budget** — the bound holds 6 of 6 and a feasible threshold flags
  **26 – 46 % of every cell on the map** against a **1.97 %** prevalence.

You can have the guarantee or a usable field, not both. The operating point stays a
ranking-driven forward simulation at an untuned default; **no default moved and no
lambda was adopted.**

The convention the row asked me to state (the two Round-3 verdicts disagreed here):
strict comparison, largest feasible lambda. My held-out failure count (3 of 6) sits
between the two verdicts' (2 of 6 and 5 of 6), which is what a convention difference
looks like; the artifact is the source and the test pins the convention.

## The root objection I recorded before building (`hate`)

*"The `1/(n+1)` conformal correction is borrowed rigor. Exchangeability fails twice —
the held-out fire's probabilities come from a model trained on the calibration fires,
and the correction is a fire-level term applied to a cell-level quantile. If the
negative result only holds because of a correction that doesn't apply, the negative
result is decoration too."*

Cheapest test: compute both columns and see whether the conclusion survives without
the correction. **The objection was half right and it changed the document's shape.**
The conclusion does not rest on the correction — but neither does it rest on the
uncorrected column, which fails held-out. Each column alone is weak; together they
are the finding, and I would have shipped only the corrected one without running the
test. The exchangeability half of the objection stands and is now a labelled caveat
in all three places: the corrected column is an *optimistic* bound on what a real
guarantee would cost, and even the optimistic version is unusable.

## The lap could not write its own report at first, and that was a real defect

`scripts/auto/report.py` and `scripts/auto/dashboard.py` were **both unparseable
on Python 3.11** — the interpreter in this sandbox and on the `auto-gates`
runner. Python 3.11 rejects a backslash anywhere inside an f-string *expression*;
PEP 701 relaxed that in 3.12. Commit `94937ab` added an `"...\n\n..."` fallback
inside `report.py`'s body f-string and an escaped-quote chip inside
`dashboard.py`'s, so both parse on a 3.12+ machine and raise `SyntaxError` at
import everywhere else, before any logic runs. **No lap could have written a
report or rebuilt the board since that commit**, and the `report-email` workflow
would have failed the same way.

It survived a push because nothing reads these files as code: `make verify` greps
them as text, `pytest` never collected them, and `check_declared_deps.py`
tolerates a file it cannot parse. They were the one code path in this repository
with no gate behind them — and the path that produces the loop's only output the
author sees.

Fixed by hoisting both values into variables (no behaviour change), and closed as
a failure class by **`tests/test_auto_loop_tooling_parses.py`**: every file under
`scripts/auto/` must `ast.parse` on the interpreter running the suite, with the
known cause named in the failure message. Filed in `docs/auto/MEMO.md` with the
next step — a test that actually *runs* `report.py` against a fixture summary,
