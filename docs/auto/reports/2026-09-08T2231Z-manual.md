## Why it failed only on GitHub

It does not reproduce here: `gates.py --mode full` is green in the sandbox at both `7eeccab` and
`1fa0b7f` (1763 passed, 63 skipped, 2 xfailed), and `scripts/check_finals_acts.py` drives all four
acts to four screenshots on Chromium 141.0.7390.37. But the difference is **not** the runner's
browser, which is where the last two laps looked.

`scripts/check_finals_acts.py:_free_port()` bound an ephemeral port, closed it, and passed the
number to Chromium — which bound it again some hundreds of milliseconds later. That gap is a
TOCTOU race, and a GitHub runner is busy enough that something else takes the port; the sandbox,
which runs almost nothing else, essentially never loses it. Chromium does **not** fail when it
cannot bind the debugging port. It logs

    ERROR:net/socket/socket_posix.cc:153] bind() failed: Address already in use (98)

and keeps running with no DevTools endpoint, so the driver polls a port nobody is listening on for
the full 30 s and reports `Connection refused`.

**The evidence that settles it, and that was in the failed run's log all along:** the runner's own
cleanup prints `Terminate orphan process: pid (2032) (chrome)`. Chromium was alive at the end of
the job. Both previous readings of this failure — WFG-196's row and `b7c1837`'s commit message —
say "a browser that died at startup", and that is the sentence this lap withdraws. It never died.

Reproduced deliberately rather than argued: holding the chosen port open across the launch prints
that exact `bind() failed` line, leaves Chromium alive, and yields `Connection refused` for the
whole window — the CI symptom exactly. Launching with port 0 instead yields a live endpoint.

## What changed

Test/driver harness only. No artifact, no registered number, no judge-facing prose.

- **`scripts/check_finals_acts.py`** — the port is no longer chosen by this repository. Chromium is
  asked for `--remote-debugging-port=0`, picks its own port, and writes it to `DevToolsActivePort`
  in the profile directory, which the new `_launch()` reads back. The race cannot occur. This is
  how Playwright and puppeteer resolve the same problem.
- Three things the same defect hid, and the reason it took two laps to see:
  Chromium's stderr went to `DEVNULL`, so the one line naming the cause was discarded on every run
  (kept and reported now); the launcher never polled the process, so a browser that genuinely died
  still cost the full 30 s (now fails in 0.1 s with its stderr); and the launch now retries once
  against a fresh profile and **fails rather than skips** when both attempts get no port.
- **`tests/test_finals_acts.py`** — the skip discriminates by exception **type**
  (`BrowserLaunchError`, raised at exactly one place by the launcher) instead of matching the words
  「no page target on port」 in a message any source could produce.
- **`docs/auto/BACKLOG.md`** — WFG-196 keeps `todo`. The retry-then-fail half of its done-when is
  done here and the measured cause corrects the row's own stated reading; the other half (something
  red when a full run yields neither a passing browser test nor four screenshots) is untouched.

## In plain terms

The nightly check went red again, and the reason turned out to be a bug in our own test code
rather than anything wrong with the project or with GitHub. Our code picked a network port for the
browser, let go of it, and then asked the browser to grab it — and on GitHub's busy machines
something else grabbed it first. The browser then sat there running with nothing listening, and the
check waited and gave up. The last two attempts at this blamed "the browser crashed on GitHub",
which was wrong: GitHub's own log shows the browser was still alive at the end.

It is fixed properly now: the browser picks its own port and tells us which one, so nothing can
take it first. I also stopped throwing away the browser's error output, which is what hid this for
two days, and the check now tries twice before failing instead of giving up quietly.

Nothing you need to do. `Main` was never blocked by this one (only the screenshot job failed, and
promotion doesn't depend on it), so no decision is waiting on you. The one thing still open is
WFG-196's other half: if the demo screenshots ever vanish entirely, no gate would shout about it
yet.
